คิวบันทึกจำนวนนับเมื่อกรอกลังและชิ้น

Date: 2026-10-26 Owner: StockCount Pro Scope: /tablet/count/[documentId] · Counter / Supervisor

Goals / Non-goals

Goals

  • กรอกลังแล้วกรอกชิ้นต่อได้ทันที แม้คำขอบันทึกลังยังไม่กลับมา และแม้เน็ตช้า
  • จำนวนล่าสุดบนจอต้องถูกบันทึก ไม่ถูกผลของรอบแรกทับ และไม่ขึ้นบันทึกไม่สำเร็จเพียงเพราะตอบช้า
  • เมื่อเน็ตขาดจริง ผู้ใช้กด บันทึกอีกครั้ง ได้โดยไม่ต้องลบจำนวน
  • คนอื่นบันทึกทับรายการเดียวกัน ยังหยุดให้ตรวจ และกด ใช้ข้อมูลของระบบ ได้เหมือนเดิม

Non-goals

  • ไม่เปลี่ยน dialog ยืนยันจำนวนครั้งแรกทีละช่อง
  • ไม่เปลี่ยนการแปลงชิ้นที่ครบลัง (convertPieceOverflowToCase)
  • ไม่ให้บันทึกของเราทับจำนวนของคนอื่นอัตโนมัติ
  • ไม่เพิ่ม timeout ที่ยกเลิกคำขอที่ยังค้างอยู่

Current state

  • ยืนยันจำนวนแล้วหน้ารอ 1 วินาที (AUTO_SAVE_DELAY_MS) แล้วส่ง PATCH หนึ่งรายการ พร้อม baseRevision ที่จับไว้ตอนกดยืนยัน
  • รายการที่ยังไม่เคยบันทึก รอบแรกสร้าง revision 1 รอบสองที่ส่งระหว่างรอบแรกยังค้างจะใช้ revision เก่า เซิร์ฟเวอร์ตอบ 409 หน้าจอขึ้น บันทึกไม่สำเร็จ
  • เมื่อรอบแรกสำเร็จ หน้าเอาจำนวนทั้งก้อนจากเซิร์ฟเวอร์มาทับ state ทำให้ชิ้นที่กรอกไว้ระหว่างรอหาย
  • คำขอไม่มี abort ตามเวลา เน็ตช้าจึงทำให้หน้าต่างชนกันนานขึ้น ป้าย กำลังบันทึก... ค้างจนกว่าจะตอบหรือเน็ตขาด
  • กดสรุปและส่งจะรออย่างมาก 30 วินาที (FLUSH_PENDING_SAVES_MAX_MS) ถ้ายังไม่จบจะไม่พาไปหน้าสรุป และ toast ว่าบันทึกบางรายการไม่สำเร็จ
  • การ์ดที่มีคนอื่นทับมีแถบแดงและปุ่ม ใช้ข้อมูลของระบบ ไม่มีปุ่มส่งจำนวนเดิมอีกครั้งเมื่อเน็ตขาด

User workflow

  1. เปิดหน้านับ เลือกสินค้า กรอกจำนวนลัง แล้วยืนยัน
  2. กรอกจำนวนชิ้นต่อได้เลย ไม่ต้องรอให้ลังขึ้นบันทึกแล้ว
  3. ระหว่างรอเน็ต ป้ายเป็น กำลังบันทึก... จำนวนที่กรอกยังอยู่บนจอ
  4. เมื่อทุกรอบของรายการนั้นสำเร็จ ป้ายเป็น บันทึกแล้ว
  5. ถ้าขึ้น บันทึกไม่สำเร็จ โดยไม่มีแถบแดง ผู้ใช้กด บันทึกอีกครั้ง จำนวนบนจอถูกส่งซ้ำ
  6. ถ้ามีแถบแดงว่ามีคนบันทึกทับ ผู้ใช้กด ใช้ข้อมูลของระบบ หรือกรอกจำนวนที่นับได้ใหม่หลังกดปุ่มนั้น
  7. กด สรุปและส่งให้หัวหน้างาน ได้เมื่อไม่มีรายการที่ยังกำลังบันทึกหรือบันทึกไม่สำเร็จ

Data model / API

  • ไม่เพิ่ม field ใน DB และไม่เปลี่ยนสัญญา PATCH .../entries/[lineId]
  • แต่ละบรรทัดมีคำขอที่กำลังส่งได้ครั้งละหนึ่งรายการ ถ้ามีคำขอค้างอยู่ การแก้ถัดไปเขียนทับ payload ที่รออยู่เท่านั้น
  • baseRevision ถูกใส่ตอนจะส่ง จากเลขแก้ไขล่าสุดที่ได้จากเซิร์ฟเวอร์หรือจากตอนโหลดเอกสาร ไม่ใช้ revision 0 ที่ใส่ไว้ชั่วคราวบนจอ
  • รอบที่ส่งตามหลังรอบแรกใช้ clientMutationId ใหม่ รอบที่ยังไม่ถูกส่งและถูกแทนที่ก่อนยิง ใช้ id เดิมได้
  • เมื่อรอบแรกสำเร็จและยังมี payload รออยู่ ให้นำ revision / ผู้บันทึก / เวลาจากผลตอบกลับมาใส่ในแถวบนจอ แต่คงจำนวนลัง แพ๊ค ชิ้นที่ผู้ใช้กรอกล่าสุด แล้วส่ง payload นั้นทันทีโดยไม่รออีก 1 วินาที
  • แถวยังถือว่ายังไม่พร้อมถูก poll ทับ ตราบใดที่กำลังส่งหรือมี payload รออยู่
  • แยกตัวตัดสินใจนี้เป็นฟังก์ชันบริสุทธิ์ที่ทดสอบได้: รับผลเซิร์ฟเวอร์ จำนวนบนจอ และ payload ที่รออยู่ แล้วคืนจำนวนที่จะโชว์ คำขอถัดไป หรือสถานะขัดแย้ง
